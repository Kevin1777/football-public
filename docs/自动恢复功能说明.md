# 自动恢复功能说明

## 概述

系统现在具备自动检测和恢复中断采集任务的能力，无需人工干预即可在各种中断情况下自动尝试继续采集。

## 核心特性

### ✅ 自动检测中断

- **状态监控**: 每 5 分钟检测一次所有采集会话
- **超时检测**: 运行中的会话超过 30 分钟无更新 → 判定为中断
- **暂停检测**: 自动发现状态为`paused`的会话

### ✅ 智能重试机制

- **分级延迟**: 第 1 次 1 分钟后、第 2 次 3 分钟后、第 3 次 5 分钟后
- **最大次数**: 默认最多重试 3 次
- **自动放弃**: 超过最大次数后停止重试

### ✅ 状态跟踪

- **重试计数**: 记录每个会话的重试次数
- **恢复历史**: 保存所有恢复尝试的记录
- **自动清理**: 定期清理 7 天前的旧记录

## 工作流程

```
采集任务运行
    ↓
检测到中断（异常/关闭/超时）
    ↓
标记为 paused/中断
    ↓
自动恢复服务检测（每5分钟）
    ↓
判断是否可以重试
    ↓
等待重试延迟
    ↓
自动触发恢复
    ↓
重新开始采集（跳过已处理）
```

## 中断场景示例

### 场景 1：网络中断

```
情况：采集过程中网络临时中断
结果：
  - 系统标记会话为paused
  - 5分钟后自动检测到
  - 1分钟延迟后自动恢复
  - 从中断位置继续采集
```

### 场景 2：服务器重启

```
情况：服务器意外重启
结果：
  - 重启后自动恢复服务启动
  - 检测到未完成的会话
  - 自动尝试恢复
  - 继续未完成的采集
```

### 场景 3：手动中断

```
情况：用户关闭浏览器或Ctrl+C
结果：
  - 会话被标记为paused
  - 下次启动时自动检测
  - 根据配置自动/手动恢复
```

## API 接口

### 1. 查看恢复状态

```bash
GET /api/progress/recovery/status
```

**响应示例:**

```json
{
  "success": true,
  "running": true,
  "check_interval": 300,
  "interrupted_count": 2,
  "interrupted_sessions": [
    {
      "session_id": "20251121_093000",
      "status": "paused",
      "recovery_info": {
        "retry_count": 1,
        "max_retries": 3,
        "can_retry": true,
        "next_retry_delay": 180
      }
    }
  ]
}
```

### 2. 手动触发恢复

```bash
POST /api/progress/recovery/manual/{session_id}
```

**示例:**

```bash
curl -X POST http://localhost:5001/api/progress/recovery/manual/20251121_093000
```

**响应:**

```json
{
  "success": true,
  "message": "已触发会话 20251121_093000 的恢复"
}
```

## 配置说明

恢复配置文件：`progress/recovery_config.json`

```json
{
  "enabled": true,
  "auto_retry": true,
  "max_retries": 3,
  "retry_intervals": [60, 180, 300],
  "recovery_sessions": {
    "20251121_093000": 1
  }
}
```

### 配置项说明

| 配置项            | 说明             | 默认值           |
| ----------------- | ---------------- | ---------------- |
| `enabled`         | 是否启用自动恢复 | `true`           |
| `auto_retry`      | 是否自动重试     | `true`           |
| `max_retries`     | 最大重试次数     | `3`              |
| `retry_intervals` | 重试延迟（秒）   | `[60, 180, 300]` |

## 使用示例

### 查看中断的会话

前端访问：

```
http://localhost:5001/collect
```

点击"📋 历史会话"按钮，查看所有会话状态。

### API 查询

```javascript
fetch("/api/progress/recovery/status")
  .then((res) => res.json())
  .then((data) => {
    console.log("中断会话数:", data.interrupted_count);
    data.interrupted_sessions.forEach((s) => {
      console.log(`- ${s.session_id}: 重试${s.recovery_info.retry_count}次`);
    });
  });
```

### 手动触发恢复

```javascript
// 方法1：通过API
fetch("/api/progress/recovery/manual/20251121_093000", {
  method: "POST",
})
  .then((res) => res.json())
  .then((data) => {
    if (data.success) {
      alert("恢复已触发");
    }
  });

// 方法2：通过前端恢复功能
// 在"历史会话"中选择会话ID
// 点击"恢复采集"按钮
```

## 最佳实践

### ✅ 推荐做法

1. **保持默认配置**

   - 默认配置适合大多数场景
   - 3 次重试足够应对临时问题

2. **查看日志**

   - 定期检查恢复日志
   - 关注重复失败的会话

3. **手动干预**

   - 超过 3 次仍失败 → 检查根本原因
   - 必要时手动修复后重启

4. **网络优化**
   - 使用稳定的网络环境
   - 考虑设置重试间隔更长

### ⚠️ 注意事项

1. **重复恢复**

   - 系统会自动避免重复恢复
   - 已处理的比赛会自动跳过

2. **资源占用**

   - 自动恢复会消耗系统资源
   - 如不需要可手动关闭

3. **数据一致性**
   - 恢复后会继续从断点开始
   - 不会重复采集已成功的数据

## 故障排查

### 问题 1：自动恢复不工作

**检查项：**

- 自动恢复服务是否启动
- `recovery_config.json`中`enabled`是否为`true`
- 检查后端日志是否有错误

**解决：**

```bash
# 重启服务
python app.py

# 检查状态
curl http://localhost:5001/api/progress/recovery/status
```

### 问题 2：重试次数用完

**原因：**

- 网络持续不稳定
- 数据源异常
- 系统资源不足

**解决：**

```bash
# 1. 检查根本原因
# 2. 修复问题后，删除恢复记录
rm progress/recovery_config.json

# 3. 重启服务，重新计数
```

### 问题 3：恢复速度慢

**调整配置：**

```json
{
  "retry_intervals": [30, 60, 120] // 缩短延迟
}
```
