## 实现的功能

### 1. 进度管理器 (`backtest/progress_manager.py`)

**核心类**: `ProgressManager`

**主要功能**:

- ✅ 创建采集会话，记录起止日期、总比赛数等信息
- ✅ 实时更新采集进度（成功/失败/跳过）
- ✅ 记录每场比赛的处理状态，支持去重
- ✅ 记录失败比赛的详细信息（比赛、原因、时间）
- ✅ 支持会话暂停和恢复
- ✅ 自动导出失败比赛日志到独立文件
- ✅ 查询会话列表和详情

**文件结构**:

```
progress/
├── session_<session_id>.json      # 会话进度文件
├── failed_<session_id>.json       # 失败比赛日志
└── ...
```

### 2. 流式采集 API 增强 (`app.py`)

**路由**: `/api/collect/batch_range_stream`

**新增功能**:

- ✅ 支持 `resume_session_id` 参数，恢复中断的采集
- ✅ 自动创建采集会话并返回 `session_id`
- ✅ 实时记录每场比赛的处理状态
- ✅ 断点续传：自动跳过已处理的比赛
- ✅ 客户端断开时自动标记会话为"暂停"
- ✅ 采集完成时自动导出失败日志

**工作流程**:

```
1. 用户启动采集 → 创建会话
2. 逐场采集比赛 → 实时记录进度
3. 发生中断     → 标记会话为"暂停"
4. 用户恢复采集 → 使用 session_id 恢复
5. 自动跳过已处理 → 继续未完成的采集
6. 采集完成     → 导出失败日志
```

## 使用场景

### 场景 1: 网络不稳定环境

**问题**: 托管采集时网络经常中断

**解决方案**:

1. 启动采集时记下 `session_id`
2. 网络中断后，使用 `resume_session_id` 恢复
3. 系统自动跳过已采集的比赛
4. 只采集未完成的部分

### 场景 2: 大批量采集

**问题**: 采集 1000+场比赛，担心中途失败

**解决方案**:

1. 分多次采集，每次记录 `session_id`
2. 每次采集前检查上次的失败日志
3. 有针对性地重试失败的比赛
4. 最终汇总所有成功的采集

### 场景 3: 系统重启

**问题**: 服务器需要重启维护

**解决方案**:

1. 重启前记录当前的 `session_id`
2. 重启后使用 `resume_session_id` 恢复
3. 系统从断点处继续采集

## 技术实现细节

### 1. 比赛唯一标识生成

```python
def _generate_match_key(match_info):
    """生成比赛唯一标识"""
    home = match_info.get('home')
    away = match_info.get('away')
    kickoff = match_info.get('kickoff')

    # 格式: 日期_主队_客队_时间
    return f"{date_part}_{home}_{away}_{time_part}"
```

**特点**:

- 唯一性：相同比赛生成相同标识
- 可读性：包含日期、队名、时间
- 稳定性：不依赖外部 ID

### 2. 断点续传判断

```python
def is_match_processed(session_id, match_info):
    """检查比赛是否已处理"""
    session_data = load_session(session_id)
    match_key = _generate_match_key(match_info)
    return match_key in session_data['processed_matches']
```

**优势**:

- 快速查询：使用列表查找
- 准确去重：基于唯一标识
- 状态无关：不管成功/失败/跳过，都算已处理

### 3. 实时进度更新

```python
def update_progress(session_id, match_info, status, current_date, error_reason=None):
    """更新采集进度"""
    # 1. 加载会话
    session_data = load_session(session_id)

    # 2. 生成唯一标识
    match_key = _generate_match_key(match_info)

    # 3. 避免重复记录
    if match_key in session_data['processed_matches']:
        return

    # 4. 更新进度计数
    session_data['progress']['processed'] += 1
    session_data['processed_matches'].append(match_key)

    # 5. 记录失败信息
    if status == 'failed':
        session_data['failed_matches'].append({
            'match_key': match_key,
            'error_reason': error_reason,
            'failed_at': datetime.now().isoformat()
        })

    # 6. 持久化保存
    save_session(session_id, session_data)
```

**特点**:

- 立即保存：每处理一场比赛就保存
- 防止重复：已处理的不会再次记录
- 详细记录：失败原因、时间都记录

### 4. 会话状态管理

**状态流转**:

```
running  → 采集中
  ↓
paused   → 暂停（可恢复）
  ↓
completed → 已完成
```

**状态判断**:

- `running`: 正在采集
- `paused`: 中断但可恢复
- `completed`: 采集完成，已导出日志

## 优势和限制

### ✅ 优势

1. **可靠性**

   - 每场比赛处理后立即保存进度
   - 支持任意时刻中断和恢复
   - 不会重复采集已成功的比赛

2. **可追溯性**

   - 详细的失败日志，包含原因和时间
   - 会话历史可查询
   - 便于故障排查

3. **易用性**

   - API 简单直观
   - 自动管理会话
   - 无需手动维护状态

4. **扩展性**
   - 支持并发会话
   - 可扩展到其他采集任务
   - 便于集成到自动化流程

### ⚠️ 限制

1. **文件管理**

   - 会话文件不会自动清理
   - 需要定期手动清理旧会话

2. **队名匹配**

   - 依赖队名和时间的一致性
   - 队名变化可能导致无法识别

3. **存储开销**
   - 每个会话都会保存文件
   - 大量会话可能占用较多磁盘空间
