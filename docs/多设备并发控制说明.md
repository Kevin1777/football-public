# 多设备并发控制说明

## 🔒 核心功能

系统现在具备**采集任务互斥锁**机制，确保：

- ✅ 同一时间只允许一个采集任务运行
- ✅ 多设备访问不会破坏正在运行的任务
- ✅ 自动检测并提示任务冲突

## 工作原理

### 1. 服务器端锁机制

```python
# 采集任务锁
collection_lock = threading.Lock()
active_collection_session = None  # 当前活动会话ID
```

**特点**:

- 使用线程锁保证互斥
- 记录当前运行的会话 ID
- 自动在任务结束时释放

### 2. 采集流程

```
设备A点击采集
  ↓
尝试获取锁 ✅
  ↓
开始采集（锁定）
  ↓
[设备B访问]
  ↓
尝试获取锁 ❌
  ↓
提示"任务正在运行"
  ↓
等待或查看历史会话
```

### 3. 自动释放

无论任务成功、失败还是中断，锁都会自动释放：

```python
try:
    # 采集逻辑
finally:
    active_collection_session = None
    collection_lock.release()
```

## 使用场景

### 场景 1：服务器运行，多人访问

**环境**:

- 服务器: `192.168.1.100:5001`
- 用户 A: 电脑访问
- 用户 B: 手机访问

**流程**:

1. 用户 A 开始采集 → 获取锁成功
2. 用户 B 访问页面 → 自动提示"正在采集中"
3. 用户 B 查看历史会话 → 可以看到 A 的采集进度
4. 用户 A 完成/中断 → 自动释放锁
5. 用户 B 可以开始新的采集

### 场景 2：采集中断后恢复

**步骤**:

1. 设备 A 开始采集
2. 网络中断/关闭浏览器
3. 设备 B 访问 → 看到"正在采集中"
4. 等待 5 分钟 → 自动恢复服务检测到中断
5. 任务暂停 → 锁自动释放
6. 设备 B 可以继续采集（断点续传）

### 场景 3：同一设备多标签页

**问题**: 用户打开多个标签页，每个都点击采集

**解决**:

- 第一个标签页获取锁成功
- 其他标签页显示"任务正在运行"
- 防止重复采集造成冲突

## API 接口

### 查询采集状态

```bash
GET /api/collect/status
```

**响应**:

```json
{
  "success": true,
  "is_collecting": true,
  "active_session": "20251121_120000",
  "message": "正在采集（会话: 20251121_120000）"
}
```

**字段说明**:

- `is_collecting`: 是否有任务正在运行
- `active_session`: 当前活动的会话 ID
- `message`: 状态描述

### 前端使用

```javascript
// 检查采集状态
async function checkCollectionStatus() {
  const response = await fetch("/api/collect/status");
  const data = await response.json();

  if (data.is_collecting) {
    alert(`任务正在运行（会话: ${data.active_session}）`);
    return true;
  }
  return false;
}

// 开始采集前检查
if (await checkCollectionStatus()) {
  alert("请等待当前任务完成！");
  return;
}
```

## 异常处理

### 1. 锁未正常释放

**现象**: 采集已结束但锁仍然占用

**原因**:

- 程序异常崩溃
- 强制终止进程

**解决**: 重启服务

```bash
# 停止服务 (Ctrl+C)
# 重新启动
python app.py
```

### 2. 查看是否有僵尸锁

通过 API 检查：

```bash
curl http://localhost:5001/api/collect/status
```

如果显示`is_collecting: true`但实际没有任务，重启服务。

### 3. 手动清理会话

```bash
# 查看运行中的会话
curl http://localhost:5001/api/progress/sessions | grep running

# 如果确认已经不在运行，手动标记完成
curl -X POST http://localhost:5001/api/progress/session/会话ID/complete
```

## 最佳实践

### ✅ 推荐做法

1. **单点发起**

   - 由一个设备发起采集
   - 其他设备查看进度

2. **查看而非重复**

   - 看到"正在采集"提示
   - 通过历史会话查看进度
   - 等待完成后再操作

3. **及时恢复**
   - 采集中断后尽快恢复
   - 使用断点续传功能
   - 避免长时间占用锁

### ⚠️ 避免的做法

1. **多设备同时点击**
   - 虽然有锁保护，但会造成不必要的请求
2. **频繁刷新页面**

   - 会重复发起状态检查
   - 增加服务器负担

3. **强制终止任务**
   - 应该让任务自然完成或中断
   - 强制终止可能导致锁未释放

## 技术细节

### 线程锁实现

```python
collection_lock = threading.Lock()

# 尝试获取锁（非阻塞）
if not collection_lock.acquire(blocking=False):
    # 获取失败，说明有任务正在运行
    return error_response()

try:
    # 执行采集任务
    active_collection_session = session_id
    do_collection()
finally:
    # 无论如何都释放锁
    active_collection_session = None
    collection_lock.release()
```

### 优点

- ✅ 线程安全
- ✅ 自动释放
- ✅ 非阻塞检测
- ✅ 支持并发查询

### 局限性

- ⚠️ 进程重启后锁失效
- ⚠️ 仅适用于单进程部署
- ⚠️ 不支持分布式部署

## FAQ

### Q1: 多服务器部署怎么办？

**A:** 当前方案不支持多服务器。如需分布式部署，建议：

- 使用 Redis 实现分布式锁
- 或使用消息队列（Celery）

### Q2: 如何让其他设备看到采集进度？

**A:** 方法：

1. 点击"📋 历史会话"
2. 找到`running`状态的会话
3. 查看实时进度

未来可以考虑实现 WebSocket 实时推送。

### Q3: 锁超时怎么办？

**A:** 目前没有超时机制。如果采集异常卡住：

- 自动恢复服务会在 30 分钟后检测
- 或手动重启服务释放锁
