# 断点续传使用指南

## 功能概述

在托管状态下进行明细采集时，如果遇到网络中断、系统重启或其他原因导致采集中断，现在支持断点续传功能，可以从中断的地方继续采集，避免重复劳动。

## 核心功能

### 1. 自动进度记录

- 每场比赛的采集状态（成功/失败/跳过）都会被自动记录
- 采集会话会被保存到 `progress/` 目录
- 失败的比赛会被详细记录，包括失败原因和时间

### 2. 断点续传

- 如果采集中断，可以使用会话 ID 恢复进度
- 已经采集成功的比赛会自动跳过
- 只采集未处理的比赛

### 3. 失败日志

- 采集完成后，会自动生成失败比赛日志
- 日志保存在 `progress/failed_<session_id>.json`
- 包含详细的失败原因、比赛信息和时间戳

## 使用方法

### 方法一：通过 API（推荐）

#### 1. 启动新的采集任务

```bash
curl -X POST http://localhost:5001/api/collect/batch_range_stream \
  -H "Content-Type: application/json" \
  -d '{
    "start_date": "2025-11-01",
    "filter_by_handicap": true,
    "skip_cached": true
  }'
```

**响应示例：**

```json
{
  "type": "session_created",
  "session_id": "20251120_225830"
}
```

记下这个 `session_id`，以便需要时恢复。

#### 2. 如果采集中断，使用会话 ID 恢复

```bash
curl -X POST http://localhost:5001/api/collect/batch_range_stream \
  -H "Content-Type: application/json" \
  -d '{
    "start_date": "2025-11-01",
    "filter_by_handicap": true,
    "skip_cached": true,
    "resume_session_id": "20251120_225830"
  }'
```

系统会：

- ✅ 自动跳过已成功采集的比赛
- ✅ 从中断的地方继续采集
- ✅ 保持原有的进度记录

## 常见场景

### 场景 1：网络中断后恢复

1. **采集过程中网络中断**

   - 系统会自动保存当前进度
   - 会话状态变为 `paused`

2. **网络恢复后继续采集**

   ```bash
   # 使用之前的 session_id 恢复
   curl -X POST http://localhost:5001/api/collect/batch_range_stream \
     -H "Content-Type: application/json" \
     -d '{
       "start_date": "2025-11-01",
       "resume_session_id": "20251120_225830"
     }'
   ```

3. **系统会自动跳过已采集的比赛，从中断处继续**

### 场景 2：查看未采集成功的比赛

采集完成后，查看失败日志：

```bash
curl http://localhost:5001/api/progress/session/20251120_225830/failed
```

分析失败原因：

- `明细抓取失败` → 网络问题，可重试
- `数据已清空` → 比赛太久远，必发网已删除数据
- `解析失败` → 页面结构变化，需更新代码

### 场景 3：手动重试失败的比赛

1. 获取失败比赛列表
2. 提取失败比赛的信息
3. 单独重新采集这些比赛

```python
import requests

# 获取失败比赛
response = requests.get('http://localhost:5001/api/progress/session/20251120_225830/failed')
failed_data = response.json()

# 提取可重试的比赛（排除数据已清空的）
retry_matches = []
for match in failed_data['failed_matches']:
    if '数据已清空' not in match['error_reason']:
        retry_matches.append({
            'home': match['home'],
            'away': match['away'],
            'kickoff': match['kickoff'],
            'label': match['match_label']
        })

print(f"可重试的比赛数: {len(retry_matches)}")
```

## 注意事项

### ✅ 优势

- **避免重复采集**：已成功的比赛不会再次采集
- **详细的失败记录**：知道哪些比赛失败了、为什么失败
- **灵活恢复**：可以随时中断、随时恢复
- **数据安全**：所有进度都持久化保存

### ⚠️ 限制

- 会话文件不会自动清理，需要手动管理
- 恢复采集时，必须使用相同的 `start_date` 参数
- 如果修改了队名或时间，可能导致无法正确识别已处理的比赛

### 💡 最佳实践

1. **记录会话 ID**：每次启动采集时，记下 `session_id`
2. **定期检查失败日志**：采集完成后及时查看失败原因
3. **网络稳定环境**：尽量在网络稳定的环境下运行
4. **分批采集**：大批量采集时，建议分多个小批次进行

## 技术细节

### 进度记录机制

- 每处理一场比赛，立即更新进度文件
- 使用比赛唯一标识（日期*主队*客队\_时间）去重
- 支持三种状态：`success`、`failed`、`skipped`

### 断点续传原理

- 读取会话文件中的 `processed_matches` 列表
- 对比待采集比赛列表，自动跳过已处理的
- 继续从未处理的比赛开始采集

### 失败原因分类

1. **网络错误**：`网络超时`、`连接失败`
2. **数据问题**：`数据已清空`、`页面结构变化`
3. **系统问题**：`磁盘空间不足`、`权限错误`

## 故障排查

### 问题 1：无法恢复会话

**症状**：提示"会话不存在或已完成"

**解决方法**：

```bash
# 检查会话是否存在
ls progress/session_*.json

# 查看会话状态
curl http://localhost:5001/api/progress/session/<session_id>
```

### 问题 2：重复采集已成功的比赛

**症状**：恢复后仍在重新采集之前成功的比赛

**原因**：比赛信息（队名、时间）发生了变化

**解决方法**：

- 确保使用相同的数据源
- 检查会话文件中的 `processed_matches` 格式

### 问题 3：失败日志为空

**症状**：采集完成但没有生成失败日志

**原因**：所有比赛都采集成功了

**验证**：

```bash
curl http://localhost:5001/api/progress/session/<session_id>
# 查看 progress.failed 是否为 0
```
