# 推送调度系统使用说明

## 概述

新的推送调度系统采用**主动调度**机制，解决了之前"轮询窗口"容易错过比赛的问题。

### 旧机制（轮询）vs 新机制（调度）

| 对比项       | 旧机制（轮询）                  | 新机制（调度）                 |
| ------------ | ------------------------------- | ------------------------------ |
| **方式**     | 每 5 分钟检查一次，匹配时间窗口 | 提前为每场比赛创建专属推送任务 |
| **精确度**   | 依赖时间窗口，有遗漏风险        | 精确到点，不会遗漏             |
| **启动时间** | 服务启动晚会错过推送            | 启动时自动扫描未开始的比赛     |
| **可视化**   | 无法查看待推送任务              | 可查看所有已调度任务           |

---

## 工作流程

### 1. 服务启动时

```
服务启动 → 10秒后 → 扫描今日比赛 → 为每场比赛创建推送任务
```

比如现在是 21:40，扫描到：

- 23:00 的比赛 → 创建 22:55 的推送任务 ✅
- 21:30 的比赛 → 已开始，跳过 ⏭️

### 2. 每天 10 点自动扫描

```
每天10:00 → 扫描今日所有比赛 → 为未开始的比赛创建推送任务
```

### 3. 到点自动推送

```
比赛开始前5分钟 → 自动触发推送 → 分析比赛 → 发送推荐到企微
```

## 使用场景

### 场景 1：正常运行（推荐）

1. **提前启动服务**（比如早上或中午）
2. 服务启动 10 秒后自动扫描并调度
3. 每天 10 点自动重新扫描
4. 到点自动推送，无需干预

### 场景 2：服务启动晚了

1. 比如 21:40 启动，21:30 的比赛已经错过
2. 服务会自动跳过已开始的比赛
3. 只调度未开始的比赛（23:00）

### 场景 3：数据更新

1. 采集到新的比赛数据
2. 手动调用 `/api/push/rescan_matches`
3. 系统重新扫描并调度

## 调度逻辑

### 推送时间计算

```
推送时间 = 比赛开始时间 - 5分钟
```

比如：

- 21:30 开球 → 21:25 推送
- 23:00 开球 → 22:55 推送
- 00:30 开球（次日凌晨） → 00:25 推送

### 过滤条件

以下情况**不会**创建推送任务：

- ❌ 比赛已经开始
- ❌ 推送时间已经过了
- ❌ 任务已经存在（避免重复）

## 注意事项

1. **服务不要频繁重启**：重启会重新调度，可能导致重复推送
2. **推送历史会记录**：每场比赛只推送一次，重复推送会被跳过
3. **跨日比赛正常处理**：凌晨的比赛会在前一天 23:55 推送

## 常见问题

### Q1: 服务启动没有自动扫描？

- 检查日志是否有错误
- 确认 `data/YYYY/MM/DD/标盘指数_latest.json` 文件是否存在

### Q2: 某场比赛没有创建推送任务？

可能原因：

1. 比赛已经开始
2. 推送时间已经过了
3. 标盘数据中没有这场比赛

### Q3: 如何取消某场比赛的推送？

目前不支持取消，但推送会检查历史，如果已推送过会自动跳过。

### Q4: 调度管理器初始化失败？

检查：

1. `schedule_manager.py` 文件是否存在
2. 依赖是否完整（apscheduler 等）
3. 后台日志中的错误信息

---

## 总结

新的调度系统采用**预约制**：

- ✅ 提前知道所有比赛时间
- ✅ 为每场比赛创建专属推送任务
- ✅ 精确到点，不会遗漏
- ✅ 可视化管理，清晰可靠

不再依赖"每 5 分钟轮询"的被动机制，推送更精确、更可靠！
